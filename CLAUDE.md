# Claude workflows for ZCashReveal (2.0)

Read docs/2.0/ZECREVEAL-2.0-PLAN.md, docs/2.0/TRACKING-MATH.md and docs/2.0/RESEARCH-2026-08-DOSSIER.md before changing anything — and **docs/2.0/SNAPSHOT.md before any change that touches Redis, a Vercel variable or the publisher**, because the managed store holds an unrelated production project's live data and its rules are not a handoff's to weaken. Owner: Aqua. Claude halts before merge; Aqua merges.

## Operating model — Aqua Stack v4.1 (docs/2.0/AQUA-STACK-v4.1.png)
- L2 (Cowork) writes a handoff in `handoffs/` (§1 SCOPE · §2 READING · §3 CONTRACT · §4 DELIVERABLES · §5 binary ASSERTIONS · §6 DISPATCH HINTS). L3 (this session: lead → director-build / director-quality → crews) executes the lowest-numbered `status: open` handoff, unless the prompt names a file — and the prompt names one whenever more than one track is open (LEDGER-02 Q1). L4 (GitHub → Vercel): production promotion is always a human click.
- Session start: read this file, then `handoffs/LEDGER.md`, then the handoff. Report spawn mode first (proven by a tool attempt). Directors name every worker they spawn; subagents do not nest.
- Crews: build — ui-builder, motion-designer, chain-integrator (Sonnet), backend-api, test-engineer, researcher (Haiku); quality — design-reviewer, security-auditor, devops-deployer, docs-scribe (Haiku).
- Loop 1 PREFLIGHT (READING / FILES / DONE MEANS / INFERRED / NOT-MATCHED) before a Haiku touches an unfamiliar subsystem, anything payment/RPC/auth, a spec longer than a screen, a re-dispatch after a gate FAIL, or a mechanical-rule dispatch.
- Loop 2 status ladder on every return: `DONE` / `DONE-WITH-ASSUMPTIONS` / `BLOCKED` / `OUT-OF-DEPTH` with FILES · EVIDENCE · ASSUMPTIONS · NOTICED · UNVERIFIED.
- Loop 3 spec-author review of executed work: `MATCHES-SPEC` / `DIVERGES` / `SPEC-WAS-AMBIGUOUS`.
- A named assertion is a RULE, not a fix (LEDGER-06 Q4): an assertion the operator names in a handoff's §5 is checked across the whole tree, not at the site that prompted it. HANDOFF-06's A9 is the case: one named assertion, four live defects, three of them in files the prompting site never touched - a `/track` class ternary that tested direction before the migration branch and so made that branch unreachable for every input, a `likelyWallet` that overrode a null fee with a verdict, and a test whose title said "unknown fee" while it passed `0n`, pinning the conflation rather than the behaviour. None of the three would have been found by fixing the site that prompted A9.
- A TRUNCATED VERIFY PHASE IS REPORTED AS TWO COUNTS, NOT ONE (LEDGER-10 Q3). When a gate's verify phase dies part-way - a usage limit, a lost worker - the surviving findings are partitioned by **whether EXECUTION settles them**, and §7 reports the two counts separately. A finding that can be REPRODUCED BY RUNNING SOMETHING does not need a refuter: the reproduction is stronger evidence than any verifier's opinion, and the lead may disposition it alone (HANDOFF-10's migrations ENOENT, its circular runbook step and its broken SQL are the worked cases). A finding that can be settled ONLY BY ARGUMENT is precisely what the three-refuter design exists for; it is re-run or carried forward as UNVERIFIED, never dispositioned by the lead. "I am the least impartial reader available" is true of the second kind and false of the first, and the rule is the line between them rather than a blanket "re-run" or a blanket "the lead reads them".
- Gate budget (LEDGER-05 Q5): a gate states its verification budget in the **first line** of its return. Findings it did not verify are reported as work, listed with the others, never as a trailing log line. A round that ends with unread findings has not converged, and the lead reads them before deciding whether to ship. HANDOFF-05's round-2 gate returned 39 findings, verified 10 against an undeclared cap and logged the other 19 at the end of the run; two of those 19 were still live and both were real.
- A property test is verified by EXECUTING THE CONCRETE SCENARIO IT EXISTS TO FORBID, and by watching that scenario fail against the pre-fix code (LEDGER-08 fold 3). `numRuns` is a budget, not evidence. HANDOFF-08's A9 is the case: 300 runs of `if (m.depositAmountZat > balance) return false;` where `balance` was the sum of every deposit the match could have been drawn from - a condition no input fast-check can generate could falsify. The assertion said sigma and the test never summed. A property test that checks each element where the property quantifies over the aggregate is invisible in a green run by construction: it is not a weak test, it is a different property that happens to be true. So every property assertion carries a named worked case beside it, which is also the half a later reader can check by eye.
- EVERY §5 ASSERTION GETS A MUTATION, PROPERTY TESTS INCLUDED; an assertion verified by reading is an assertion not verified (LEDGER-08 fold 4 - L2's rule about itself, kept here because the ledger records what this project learned rather than who learned it). L2 broke twelve of HANDOFF-08's thirteen assertions and read the thirteenth, and the one it read is the one that was wrong.
- Fail-side probes (LEDGER-05 fold 7): a fail-side probe that does not fail is **itself a finding** and is reported as one. Two-polarity evidence is worthless when the negative case does not discriminate, and repairing it quietly hides that the positive result was never evidence. This has happened twice — HANDOFF-04's reused Playwright server and HANDOFF-05's zatoshi conversion — and both times the session caught it. The rule exists so the third time is caught by the rule rather than by luck. **And its converse, which is the rule a verifier needs about itself: when a probe comes back saying the code is wrong, check the probe before judging the code, and report a malformed probe rather than silently redoing it.** A probe that does not discriminate and a guard that is inert produce the same output, so the reading is not available from the result — only from re-examining the instrument. Five of L2's probes across HANDOFF-08's round 4 and HANDOFF-10 were malformed and every one of them first looked like a guard that did nothing: an object-literal probe that never reached the guard because it failed typecheck, and a runbook section deleted whole to prove `check-infra-docs` was inert when the guard was right and two of the same invocations survived elsewhere in the file. The third case is the one that shows why reporting matters more than repairing: F-43-1 named a real loose pattern in `check-infra-docs.mjs` and illustrated it with a sentence — "Take a backup before migrating" — that does not satisfy `/migrate/`, because "migrating" is migrat+ing. Executing the cited example before accepting the finding is what separated the two halves; the row was loose on a different sentence, three rows were loose rather than one, and a session that had quietly substituted a working example would have shipped the fix while leaving the reason it was needed unrecorded.
- A FAIL SIDE THAT IS ONLY A CODE MUTATION PROVES THE ASSERTION IS WIRED, NEVER THAT IT DISCRIMINATES (LEDGER-09a Q2). **At least one fail side per assertion must be a DATA mutation - a value drawn from the set the predicate claims to exclude.** Deleting a callback, throwing from a barrel, perturbing a constant, removing a copy line: all code mutations, all still welcome, none sufficient alone. The evidence is that all six instances of "an assertion satisfied by every value it was written to exclude" shipped WITH a two-polarity transcript - the rule was obeyed and did not catch them - because the fail side was chosen to fail. HANDOFF-08's A9 is the measured case: its fail side was a code change, and L2 ran the DATA mutation the assertion's own stated exclusion set names ("a match claiming more than the pool holds") against merged main and got three HIGH matches claiming 300 ZEC against a 100 ZEC pool. Structurally: **§5 states each assertion's EXCLUSION SET and §7's fail-side transcript names WHICH MEMBER it used**, so a reader sees at a glance whether the fail side came from inside the set or from outside it. `check-ledger-structure.mjs` checks that the clause is PRESENT; it cannot check that it is correct, and that limit is stated in the guard's own header so no one later reads a green run as semantic. The six instances split in two and only one half is judgement: whether a pathspec's scope intersects a deliverable's path, whether a fixture makes distinct quantities equal, and whether an assertion survives deleting its executable body are all MECHANICALLY DECIDABLE; a tautological predicate over its domain is not, and that half is what HANDOFF-13 specifies a guard for rather than building one.
- AN EXCLUSION-SET MEMBER IS CHECKED AGAINST THE SHIPPED OBJECT BEFORE IT IS WRITTEN (LEDGER-11 Q5(a)). A member the object ALREADY EXHIBITS is a defect being filed or a clause got wrong - it is never a test to write. The rule points at the author of §5 rather than at the executor: writing "the estimator must exclude X" when the shipped estimator emits X every run does not commission a test, it misfiles a bug report as an assertion, and the executing session then spends a round proving something everyone could already see.
- AND THE FOURTH AMENDMENT TO THE TWO-POLARITY RULE, WHICH IS THE ONLY LICENSED EXIT FROM THE DATA-MUTATION REQUIREMENT (LEDGER-11 Q5(c)). **When NO FIELD CAN HOLD an excluded value, the assertion is TYPE-LEVEL and its fail side is a `@ts-expect-error` on the construction, not a data mutation.** An assertion whose exclusion set is empty at every level - no value excluded, no construction rejected - is DELETED, not dressed: it asserts nothing, and a green run of it is evidence about nothing. This is a narrow exit and it is not a way around the rule one bullet up; the burden is showing the field cannot hold the value, not that no one expects it to.
- A RATE QUOTED WITHOUT ITS n IS NOT A MEASUREMENT, AND A RATE QUOTED WHILE THE SAMPLE IS STILL RUNNING IS NOT ONE EITHER (LEDGER-11 fold 10 - L2's rule about its own reporting). L2 surveyed mainnet blocks against the fixture README's selection criteria and stated the conforming count THREE TIMES before the sample finished - one, then two, then four - and an earlier draft generalised from 30 blocks spread across 26,000 heights to "§2 describes a block that does not occur", which the finished n=130 sample refuted: §2 is satisfiable, just uncommon at 3%, and the binding constraint is Sapling activity rather than the 200 KB ceiling. A partial sample is not a small sample, because the order a scan happens to run is not random with respect to what it is measuring. The report carries the n or it carries no rate.
- THE SEAM BETWEEN TWO PROCESSES IS WHERE THIS PROJECT'S TESTS AGREE WITH EACH OTHER AND DISAGREE WITH THE WIRE (LEDGER-11, the HANDOFF-11 session's own diagnosis). Three defects in one handoff had one shape: the WS envelope, the `/v2/mempool` 500 on the wire form, and `TipChannelPayload`'s missing `type`. **Each was a seam between two processes, each was covered by tests on BOTH sides, and each test BUILT ITS OWN INPUT rather than taking the other side's output.** Two suites can be exhaustive about a TYPE and both wrong about the WIRE, and neither can see it, because the disagreement lives in the gap they each stubbed. The instrument is to make one side ACTUALLY PRODUCE the value and hand it to the other - a round trip through the real serialiser and the real reviver, not a fixture that resembles one. HANDOFF-12 found the fourth instance by running that instrument before writing the code that would have shipped it: the indexer's `serializeReport` stringifies EVERY bigint regardless of key, `reviveWireZatoshi` revives only keys matching `/Zat$/`, and `ClaimAssessment` carries `rawCount`, `effectiveSetSize`, `countIn` and `countOut` - four bigints, no `Zat` suffix. Executed, four of five fields came back `string` where the declared type says `bigint`, and the `as T` cast means the compiler never objects. The defect was not in the tree yet; the instrument found it in the design.
- EVERY GUARD'S SELF-TEST ITERATES THE RULE'S OWN DATA STRUCTURE, AND EVERY DETECTOR IS DRIVEN AT LEAST ONCE OVER THE REAL TREE (LEDGER-09a Q3). Two standards, neither subsuming the other: iterating the rule's data prevents a probe set that UNDER-COVERS the rule, so a new member cannot arrive untested; driving the real tree prevents a probe that passes against a synthetic fixture and would not against reality - the directory rename that produced a silent vacuous pass. A guard's self-test IS a fail-side transcript for the guard, and hand-written probes are "chosen to fail" on the same argument as above. Two facts about guards in this project, both measured: **three of its seventeen guards have shipped with a self-test that certified a hole**, and of the twelve holes in `check-instrument-deps.mjs`, **eleven were found by executing a probe and none by reading**. The diagnostic case is that `check-instrument-deps.mjs` already met the first standard in R2 and not in R1, and the half without the loop is exactly the half that had the hole.
- CLAUSE (b) OF THE STOPPING RULE, AMENDED, AND THE AMENDMENT IS A RESTRICTION RATHER THAN A LICENCE (LEDGER-09a Q2). A recurring shape is covered when a GUARD is shown to fail on it. **Where no guard is possible, a structural requirement plus a written rule may stand in - but it is explicitly WEAKER, it must be recorded AS weaker in the ledger, and it is chosen only after a guard has been attempted and shown to be impossible.** A rule does not silently become a guard: three of seventeen guards shipped certifying a hole, and a rule has no self-test at all.
- EVERY SCRIPTED REPLACEMENT ASSERTS THAT ITS PATTERN MATCHED (LEDGER-09b Q6). A `replace(old, new)` that matches nothing is indistinguishable from one that matched, so a report can claim a fix in good faith and be false. That is the discrimination shape arriving in the EDITING TOOL rather than in a test, and it is the one face of it that is free to close. It has already cost this project twice in one session: two of HANDOFF-09b's §7 claims - migration 005's contract-003 wording and its `MS_PER_SECOND` pointer - were written as applied and were still standing a commit later, found by gate round 2 re-checking round 1's claims rather than trusting the report.
- AN EXHAUSTIVE CLAIM IS ONLY EXHAUSTIVE OVER THE THING IT ENUMERATES, AND THE THING TO ENUMERATE IS THE OBJECT THE RULE IS ABOUT - NEVER A SOURCE THAT CONSTRUCTS IT (LEDGER-09b, L2's own correction). For an index, the query sites ARE the object, so a static sweep of the tree is the right instrument and `idx_scan = 0` is only corroboration. For a database constraint, `pg_constraint` is the object and the migration files are a CONSTRUCTION HISTORY: L2 enumerated every `CREATE TABLE` in the five migrations, called it exhaustive, and missed that migration 003 widened `pool_nullifiers`' pool CHECK with an `ALTER` - so the §1 SCOPE it wrote for HANDOFF-09b rested on a false premise that the executing session caught by reading the object instead. The two halves of this rule are the same rule and neither is safe alone.
- A PROBE WHOSE OUTPUT IS AN ORDERING, A PAIRING OR AN ENUMERATION IS CHECKED AGAINST ONE KNOWN MEMBER BEFORE ANY FINDING IS BUILT ON IT (LEDGER-04a, L2's rule about its own instruments). L2's three malformed probes on this project have one shape and it is not carelessness, it is a LIST OPERATION over the wrong ordering, pairing or scope: the nav-table read that paired two extracted lists POSITIONALLY; the `pg_constraint` enumeration that read `CREATE TABLE` and missed an `ALTER` (the rule above); and `sort -u` over `font-size:` STRINGS, which sorts lexicographically, so `"10px"` precedes `"8.5px"` because `'1' < '8'` and a "smallest sizes" list began at 10 while the tree floored at 8.5 with twenty-four declarations at 9.5. **The consequence is worse than the error every time, because the finding built on it UNDERSTATES the defect and a brief that understates the defect it commissions licenses a smaller fix.** F-04a-4 said `apps/web` "already floors at 10px", which made the reader's "half the text is basically 9px" a figure of speech instead of a measurement; the only reason it did not get the smaller fix is that the executing session measured instead of believing the brief. The check is one line - ask the sorted list whether it contains a member you already know is in the set - and it is owed BEFORE the finding, not after the fix. This is the same discipline as the fail-side rule two bullets up, pointed at the instrument rather than at the code: when a probe's output is a list, the probe is the thing to test first.
- A GUARD CLOSES A SHAPE AT THE SITES IT CHECKS, NOT THE SHAPE EVERYWHERE, SO COUNT INSTANCES AGAINST THE ORIGIN AND NOT THE FACE (LEDGER-09b Q3). The origin this project is tracking: **a new workspace member or suite arrives without inheriting a convention every existing member has.** Four faces so far - a missing CI step (twice: `zebra-rpc`, then `packages/zec-instruments`), a missing vitest JSON report, and a missing `globalSetup` that cost a truncated developer database. Two guards and one register row cover those four; the origin stays open, and the count does NOT reset when a guard ships. HANDOFF-09b proved the distinction inside one week: widening `assert-no-skipped-integration.mjs` closed the missing-report face and was blind to the `globalSetup` face, which has the same origin and a different failure mode entirely.
- A FAIL SIDE THAT MUTATES A MODULE ITS AUTHOR HAS NOT READ LINE-BY-LINE IS A HYPOTHESIS ABOUT THAT MODULE, NOT A PROBE OF IT (F-56-1, LEDGER-14 Q1, adopted by L2 on PR #56). **Read it first, or label the probe UNVERIFIED.** This is NOT already what the fail-side rules mean: those govern the SHAPE of a fail side - a DATA mutation drawn from the stated exclusion set - and say nothing about whether its author has read the module the mutation lands in. The two are independent, and a probe can satisfy every shape rule while being about a module that does not work the way its author assumed. The evidence is that FOUR of HANDOFF-14's probes were wrong before the code was, all four looked exactly like product defects, and none was: a fail side that removed `chainSupply` and met a documented `valuePools` fallback its author had not read; a fixture that made two distinct supply sources equal; `U` asserted as every shielded lane when it is `sprout + orchard`; and an A3 fixture that inherited `residual: null` from the committed web fixture and then asserted it was measured. The rule's operational half is the move that caught all four and is the converse of the bullet above: **when a probe comes back saying the code is wrong, check the probe before judging the code.** Reading the module is what makes that check cheap; without it, every disagreement between a probe and a module is a coin toss the probe usually loses.
- STOPPING RULE, CLAUSE (ii), SECOND AMENDMENT, AND IT IS A SCOPE RULE RATHER THAN A ROUND BUDGET (L2's ruling on PR #46, round 7). **Once a round returns NO finding in an executable line of the PRODUCT, subsequent rounds review only (a) guard predicates and their self-tests, (b) test assertions, and (c) sentences making a CHECKABLE CLAIM ABOUT RUNTIME BEHAVIOUR - checked by EXECUTING the behaviour rather than by reading the sentence.** Everything else - rationale, framing, a table's wording, a commit message - is applied without earning a round. **AND CLAUSE (c) NOW NAMES ONE STANDING SUB-CLASS EXPLICITLY, SO IT NEVER HAS TO WAIT FOR A ROUND TO REACH IT (LEDGER-14 Q3, adopted): EVERY ROLLBACK, RECOVERY AND "STOP THE PROCESS" STEP IN AN OPERATOR DOCUMENT IS EXECUTED, NOT READ, EVERY GATE.** Such a step makes a checkable claim about runtime behaviour by construction. The case that produced it cost one grep: `CUTOVER-1.0.md` told an operator that stopping the publisher lets the site fall back "until its TTL expires", and `zecreveal:snapshot:latest` carries no TTL by design - so the operator would have stopped the process, believed they had rolled back, and left a frozen page up. That is this project's own recurring shape, a stale site that renders and reports no fault, written into the runbook meant to prevent it.  The diagnosis it comes from: HANDOFF-09b's product converged at round 5, which returned no live defect against eleven mutations, a 2,000-case randomised sweep, three throwaway-database reproductions and a 63-pair equivalence check - and the gate did not stop, because rounds 5, 6 and 7 each found defects in the RUNBOOK PROSE, REGISTER ROWS AND GUARD PREDICATES that rounds 3, 4 and 5 had written. **A gate reviewing its own output does not terminate on its own, because every fix commit adds more reviewable surface.** The first amendment bounded prose-only commits and did not bound this, because a guard predicate is not prose. Prose that does not claim a behaviour cannot carry a behavioural defect, and reviewing it finds prose defects forever; (a) through (c) are a finite greppable set, and both of round 5's HIGHs were in (c) - "a non-positive baseline publishes the series without its baseline" and "the publisher logs each one" were checkable by running the publisher, and false.
- STOPPING RULE, CLAUSE (ii), AMENDED (LEDGER-09b round 4): the fix commit is reviewed as its own commit BY A NEW ROUND, unless it changes only a message string, a severity, a comment or a document sentence - no control flow, no predicate, no schema, no fixture. Such a commit is reviewed within the round that produced it. **The regress terminates where a fix can no longer carry a behavioural defect, and not before.** The bound exists because the unbounded form regresses forever and the unbounded absence of it has now cost six consecutive sessions: the fix commit is where the finding was in HANDOFF-09a twice and in HANDOFF-09b's rounds 2, 3 and 4.
- Post-fan-out sweep: after ANY workflow or subagent fan-out returns, the lead runs `git status --porcelain` **before its next commit** and reverts every path it did not intend to change. A file a worker wrote is never carried into a commit on the assumption it is harmless — a read-only worker that writes has already shown its scope was not binding, so nothing else it did to the tree is trustworthy either. If a stray write turns out to be a good idea, the lead re-makes it deliberately. This has now happened twice (HANDOFF-04, a gate verifier writing a scratch test into the repo; HANDOFF-06, a mapping agent writing the pool widening it had been asked only to map), caught both times by a lead noticing rather than by a check — which is what makes it a rule. §7 states that the sweep was run after each fan-out and what it returned.
- Gate stopping rule (LEDGER-07 Q6, amended by LEDGER-10 fold 6), three parts, and none of them is a round budget. (i) **A round ends the gate when (a) it returns no finding a user could see AND (b) every defect SHAPE that has recurred across three or more rounds is covered by a guard shown to fail on that shape.** Clause (b) replaces the older second half, "and no finding whose fix changes behaviour", and it is what lets a round stop while a behaviour-changing fix is in it - which the old wording forbade and therefore made unsatisfiable on any branch that was still improving. The evidence is HANDOFF-08's reach curve: round 2 four HIGHs, round 3 two, round 4 one plus three in the guards themselves. A round whose findings are all defects in the guards, or statements about them, is a different condition from a round finding live defects in the estimator, and clause (b) is what names the difference. Clause (b) is not satisfied by a guard that exists: the guard must have been RUN and shown to fail on the shape, because three of round 4's six defects were in the guards and every one was found by running them. **CLAUSE (b)'s "SHAPE" IS THE FACE, NOT THE ORIGIN** - the two are distinguished in the origin-counting rule above, and clause (b) has to quantify over the face or it can never be satisfied while an origin is still producing new ones. The origin's count does not reset and the gate does not wait on it; what a round must show is that the face it just found is guarded. (ii) **The fix commit is always reviewed as its own commit, bounded as the clause (ii) amendment above states** - the review IS a new round by that amendment, and it does not consume the three-round-per-finding budget below UNLESS it re-surfaces a finding with the same fingerprint - which is precisely the repeat that budget counts, so a fix that keeps failing still reaches `NOT CONVERGING` and still goes to the operator. Without that exception the exemption would disable the escalation in the one case it exists for, because on a long gate every round after the first IS a fix-commit review. Three sessions running have shown a fix here is the most dangerous commit in the branch: it widens a union, redefines a number or narrows a predicate, and the consumer that was correct by accident is never in the diff. HANDOFF-07 measured three of round 2's five survivors and three of round 3's seven as defects the previous round's fix had created. (iii) **The lead states the extrapolation rather than claiming convergence** - "a fifth round probably finds one or two more, of this reach". A gate that claims convergence it cannot demonstrate is worse than one that stops honestly. A round budget is the wrong instrument because it counts rounds, and what decays across rounds is REACH: HANDOFF-07's round 1 dropped whole snapshots from /track and published a wallet name on no source, and its round 4 fixed a caption. A severity floor is wrong too, because severity is assigned by the reviewer that found it and this codebase's most expensive defects have twice been rated LOW.
- WHEN THE SAME DEFECT SHAPE RECURS ACROSS THREE ROUNDS, THE NEXT ROUND'S INSTRUMENT IS A GUARD, NOT ANOTHER REVIEW (LEDGER-08 round 4 fold 6; "shape" here is the FACE, on clause (b)'s reading above, for the same reason). A rule the authoring agent has violated more times than it has honoured is evidence about the instrument, not about the agent: human-shaped review finds each instance one commit after it is made, so a further round of the same instrument finds the next instance the same way and no faster. The evidence is HANDOFF-08 rounds 1-3 plus L2's F-41-1 - five instances of two shapes, the fifth committed INSIDE the commit that fixed the fourth, by a session that had just written the rule against it. The two shapes and the guards that now catch them: a discriminated union gaining a FIELD whose renderers keep reading the old ones (`check-audit-consumers.mjs` - `assertNever` protects the SET of variants and says nothing about the SHAPE of one), and a gate finding naming several sites whose fix lands in some of them (`check-finding-sites.mjs` - the finding's site list becomes data, checked on every run). A guard is warranted by RECURRENCE, not by severity: both shapes' instances were rated LOW to HIGH and the cheapest of them was the most diagnostic.
- Loop 4 bounded convergence: gate FAIL → at most 3 rounds **per finding**, fingerprinted file · rule · severity; a round that surfaces only NEW findings, from a different reviewer or a different file, is not a repeat round. `NOT CONVERGING` — the same finding resisting a third fix — goes to the operator. Never ship a known false statement about a named person to keep a counter down: escalate, or fix it and say so in §7 (LEDGER-02 Q6).
- Sweep a corrected fact (LEDGER-03 Q3): when a gate round corrects a claim of fact, grep the whole tree for every restatement of that fact, correct all of them in the same commit, and list the swept files in §7. A correction that lands in one file while another still states the error is a **HIGH** finding, not a LOW one — the site then contradicts itself about a named person, which is worse than the original error.
- Evidence: every §5 assertion gets a two-polarity transcript (pass state and fail state). Every claim in §7 carries provenance — Executed (output shown) / Read (file + commit) / UNVERIFIED (labelled). Assumptions are dispositioned ACCEPTED / CORRECTED / DEFERRED; deferrals go to §8.
- Finish: fill §7 REPORT in the handoff, append §8 to `handoffs/LEDGER.md`, add a `LOG.md` line, set `status: shipped`, open the PR (`gh pr create`, heredoc body, no emoji). **Every PR stops at opened.** No merge, no deploy, no Vercel env changes, no `docker compose up`, no branch deletion — those are operator clicks.

## Revolution protocol (handoffs/ maintains itself; no file uploads)

Every session, in this order:

1. RECONCILE — first commit on your branch, before any handoff work. Set every handoff whose PR is merged into main to `status: closed` - **a merged PR closes a handoff only when its §7 STATUS is DONE; a handoff whose PR merged PARTIAL returns to `status: open` instead**, because the kickoff line routes on `open` and a PARTIAL closed as if DONE has its remainder silently orphaned (F-50-4, LEDGER-12); set the one you are executing to `status: in-progress`; for each track (Web 01-04, Data 05-09, Infra 10, Integration 11-12) set the lowest-numbered `queued` handoff whose `depends_on` are all closed to `status: open` — exactly one open per track; rewrite the Status column of the table in handoffs/README.md to match. Commit: `chore(handoffs): reconcile status before HANDOFF-NN`.
2. L2 RESOLUTION — if the prompt contains a block fenced as `L2 RESOLUTION`, append it verbatim to handoffs/LEDGER.md beneath the ledger block of the handoff it names, then apply every instruction under its FOLDS heading. L2 (Cowork) has no write access to this repository; that block is the only channel by which verification results, answers to ledger questions and amendments to future handoffs reach you. If there is no such block, skip.
3. EXECUTE the lowest-numbered handoff with `status: open`, unless the prompt names a file — and the prompt names one whenever more than one track is open — under its §1-§6.
4. WRITE-BACK — before the PR opens: fill §7 in your own handoff and set it to `status: shipped`; append your §8 block to handoffs/LEDGER.md (append-only — never rewrite an earlier block, including L2's); add one row to handoffs/LOG.md; update the handoffs/README.md table. The PR title MUST begin `HANDOFF-NN:` — LOG.md and LEDGER.md key on the title, not the branch, because the harness names branches. Stop at **opened**.
5. ARCHIVE — save every message that steered your session to `handoffs/prompts/PROMPT-NN.md`, each verbatim under a heading naming what it is and when it arrived; one file per handoff, not one per message. The first message lands in the same commit as RECONCILE; a message that arrives mid-session is appended in the next commit (LEDGER-02 Q7).

Status flips, the README table, LEDGER appends, LOG rows and the prompt archive are the only cross-handoff edits a session makes.

**Lighthouse** (LEDGER-03 Q1, LEDGER-04 Q3): the container number, taken against `next start`, is the gate a session must clear and report. The deployed measurement is the operator's, taken in a browser and pasted into the ledger — never a handoff deliverable. A session cannot reach a preview host: Deployment Protection returns 302 to the SSO endpoint, and the session's own egress proxy refuses the CONNECT tunnel with 403 before that, so no operator toggle alone makes it reachable. The same wall stands between a session and the VPS or a live gateway.

pnpm + Turbo monorepo · packages/zec-types (shared types + DTOs) · packages/content (zod schemas + research data) · packages/zebra-rpc (typed Zebra client) · packages/zec-instruments (the three pool-level estimators and the pure leaves they need, imported by BOTH the indexer and the publisher; depends on zec-types and nothing else, and `scripts/check-instrument-deps.mjs` fails if `zeromq` or `@zcashreveal/indexer` enters its graph - that constraint is why the package exists) · apps/indexer (Node 22, Zebra RPC/ZMQ, Postgres + Redis, analysis) · apps/gateway (Fastify REST + WS) · apps/publisher (snapshot.json → file + managed Redis) · apps/web (Next.js App Router, React 19, Tailwind v4) · legacy/dashboard (v0.2, read-only).

Two Redis instances, never confused, and the second one is **shared with an unrelated production project** — full rules in `docs/2.0/SNAPSHOT.md`, which no later handoff may weaken.

- **VPS Redis** (`REDIS_URL`) carries pub/sub, `zcashreveal:mempool:live` and the anchor registry, and never leaves the box.
- **Vercel-managed Redis** is **shared with an unrelated production project**. This project owns one namespace in it, `zecreveal:snapshot:*`, and touches nothing else — three writes per block, so the public site renders even when the VPS or tunnel is down. The store `upstash-kv-blue-garden` is connected to the `zecreveal` project (Production + Preview) with variable prefix `SNAPSHOT_REDIS`, and the names it injects are `SNAPSHOT_REDIS_KV_REST_API_URL`, `SNAPSHOT_REDIS_KV_REST_API_READ_ONLY_TOKEN` (what apps/web reads — never the read-write `SNAPSHOT_REDIS_KV_REST_API_TOKEN`), `SNAPSHOT_REDIS_KV_URL` and `SNAPSHOT_REDIS_REDIS_URL` (either TCP URL for the publisher). Those are the canonical names; the older `SNAPSHOT_REDIS_URL` / `SNAPSHOT_REDIS_REST_URL` / `SNAPSHOT_REDIS_REST_TOKEN` this repo used to state are injected by nothing and were corrected in HANDOFF-05.
- Because it is shared, a mistake there is an outage for a project that never agreed to run alongside us: **every** key begins `zecreveal:` (no scratch keys, no health-check key outside it); `FLUSHDB`, `FLUSHALL`, `SWAPDB` and `SCRIPT FLUSH` are forbidden everywhere including tests, fixtures, scripts and runbooks; `KEYS` is forbidden outright and `SCAN` only with `MATCH zecreveal:*`; no `DEL` by pattern; tests and local dev never point at it; the publisher is the only writer. `scripts/check-redis-safety.mjs` enforces the command rules in CI. Budget is 500K commands/month **shared** — `SNAPSHOT_REDIS_MONTHLY_BUDGET` (default 200000) stops the publisher before this project can rate-limit the other one — charged at the WIRE count of five per tip (`MULTI` + 3 x `SET` + `EXEC`), about 172,500 a month, because Upstash's published exemption list does not name `MULTI` or `EXEC` and the allowance at risk is the other project's (LEDGER-09 Q2). Exit condition: its own database when the shared total approaches the allowance.

## Conventions
- TypeScript strict (tsconfig.base.json); ESM; `bigint` for zatoshi; heights/counts `number`; lowercase hex, no 0x; `Hex` is branded and validated at the RPC boundary.
- Pools: 'sprout' | 'sapling' | 'orchard' | 'ironwood'; generics `<P extends Pool>`; DB CHECKs mirror the union.
- Every analysis estimator is pure and emits a FilterApplication audit record {filter, params, countIn, countOut}.
- **Dropping a `NOT NULL` runs every branch the constraint kept unreachable** (LEDGER-06 Q3). A `NOT NULL` column is not only a constraint, it is a set of untested branches: every consumer's coalesce, cast and fallback has been dead code for as long as the constraint stood. Enumerate the consumers and exercise the null before shipping the migration, and expect the type checker not to help - driver row types are caller-asserted, and `Number(null)` is legal. HANDOFF-06 dropped one `NOT NULL DEFAULT 0` and three live defects fell out at once: a `/tx` render of MINUS one ZEC through a fallback that summed only resolved inputs, a `BigInt(null)` thrown into its own catch so the whole leak record was silently dropped and a successful lookup blamed for it, and an unknown fee published as `UNKNOWN_NONSTANDARD` - the same verdict as a fee measured and found non-conventional. The same reading applies to any type that widens: a union gaining a member, an optional becoming present, a narrow return type becoming nullable.
- Claim levels: >1000 aggregate_only · 100–1000 broad_candidate_set · 10–100 small_heuristic_set · ≤10 requires_disclosure. Never claim identity from public data. Never render a shielded balance without a viewing key (Mode A, client-side only).
- Content: every Record claim has sources[] (≥1), confidence (high|med|low), lastVerified; unverified items live only in unverified.json.
- Labels precedence: consensus > owner filing > exchange confirmation > analyst > behaviour — always displayed.
- Env names: public `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_WS_URL`, `NEXT_PUBLIC_SNAPSHOT_URL`, `NEXT_PUBLIC_DATA_MODE`; server-only `SNAPSHOT_REDIS_*`, `REDIS_URL`, `RATE_LIMIT_REDIS_URL`, `DATABASE_URL`, `ZEBRAD_*`. Secrets only via env; `.env.example` documents every variable with a one-line comment.

## Don'ts
**A worker scoped read-only does not write to the tree.** If it concludes the tree must change, it returns the change as a diff in its report and the lead applies it. Two occurrences, two different agent roles, both scoped read-only: HANDOFF-04's gate verifier wrote a scratch test into the repository, and HANDOFF-06's mapping agent wrote the pool widening into `shielded.ts` and `leaks.ts` when it had been asked only to map. The post-fan-out sweep that caught the second is the enforcement and stays - it is a net, not a substitute for the rule, because a worker that ignored its scope once has already shown the scope was not binding on anything else it did.

No deterministic deanonymisation claims · no emoji · no Tailwind soup outside the token layer · no secrets in git · no destructive git/docker commands without Aqua's explicit go · no per-transaction traffic to the managed Redis · no `FLUSHDB`/`FLUSHALL`/`SWAPDB`/`SCRIPT FLUSH`/`KEYS` anywhere, and no key outside `zecreveal:` — the managed store is shared with someone else's production · no agent sets a Vercel environment variable.
